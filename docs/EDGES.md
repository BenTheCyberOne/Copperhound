# Edge reference

The [reference tables](#reference) at the end list every built-in edge kind
with its meaning, abuse and remediation. The sections before them cover edges
CopperHound derives at ingest or in post-processing rather than reading from
collectors. Names follow BloodHound CE where it has an equivalent. The help text
served by `GET /api/v1/edge-kinds` (`help`) comes from `ch_model::edge_help`
(`crates/model/src/help.rs`).

Direction: a traversable edge `A -X-> B` means control of A gives control of B.
`SameForestTrust` and `CrossForestTrust` instead follow BloodHound CE and point
from the trusting domain to the trusted domain.

## Trusts

Emitted at ingest from SharpHound `Trusts` (`TrustType`, `TrustAttributes`,
`SidFilteringEnabled`, `SpoofSIDHistoryBlocked`, `TGTDelegationEnabled`;
string or numeric forms). Every trust also gets `TrustedBy`; records without
`TrustType` or `TrustAttributes` (older collectors, ldapdomaindump) get only
`TrustedBy`.

| Edge | Traversable | Source → target | Emitted when |
|---|---|---|---|
| `SameForestTrust` | yes | trusting → trusted | `TrustType` is ParentChild / CrossLink / TreeRoot / Shortcut (or `0`, `1`), or `TrustAttributes` has WITHIN_FOREST (0x20) |
| `CrossForestTrust` | **no** | trusting → trusted | any other trust type (Forest, External, Unknown) |
| `SpoofSIDHistory` | yes | trusted → trusting | cross-forest trust with SID filtering off: `SpoofSIDHistoryBlocked == false`, or, if that field is absent, `SidFilteringEnabled == false`. Unknown counts as filtered. |
| `AbuseTGTDelegation` | yes | trusted → trusting | cross-forest trust with `TGTDelegationEnabled == true` or `TrustAttributes` has CROSS_ORGANIZATION_ENABLE_TGT_DELEGATION (0x800) |
| `HasTrustKeys` | yes | trusting domain → trust account user in the trusted domain | post-processing (`postprocess/ad.rs`), for every trust (`SameForestTrust`, `CrossForestTrust` or `TrustedBy`): the trusted domain's user whose `samaccountname` (else the name before `@`) is the trusting domain's NetBIOS name + `$`. The NetBIOS name is the domain's `netbios` / `flatname` property (LDIF / AD Explorer input sets `netbios` from the crossRef), else the first label of its DNS name. The trusting domain stores the account's key (the trust key), so its DCs yield a Kerberos logon as that account in the trusted domain. |

**Forest closure** (`postprocess/ad.rs`). Inside a forest, trusts are two-way
and transitive with no SID filtering, and control of any domain yields every
other (forge a ticket with the Enterprise Admins SID in its ExtraSids, or
capture another domain's DC TGT): the forest is the security boundary. Domains
connected by `SameForestTrust` in either direction form a forest. For forests of
up to 64 domains the pass adds `SameForestTrust` between every ordered pair;
larger forests keep only their collected edges, and paths still run through the
intermediate domains. All domains are Tier Zero by default, so every forest's
Tier Zero is one set.

**SID filtering semantics.** Only `SpoofSIDHistory` and `AbuseTGTDelegation`
cross a forest boundary; a forest or external trust with SID filtering on and
TGT delegation off is not an attack path. Unlike BloodHound CE,
`CrossForestTrust` is not traversable, because the trust alone does not allow
compromise. Within a forest no `SpoofSIDHistory` edge is emitted, because
`SameForestTrust` already represents that path.

**ADCS.** ESC6b, ESC9 and ESC10 run their forest-level domain controller checks
over the DCs of every domain in the target domain's forest.

## AD

| Edge | Traversable | Semantics |
|---|---|---|
| `CoerceToTGT` | yes | An enabled User or Computer with unconstrained delegation points to its own domain, to every domain in its forest, and to every domain of a forest that trusts its forest with TGT delegation (via `AbuseTGTDelegation`). Coerce a DC (PrinterBug, PetitPotam, DFSCoerce) to authenticate to the host, capture its TGT, then DCSync. NTLM relay is not modelled. |
| `DCSync` | yes | Post-processing pass `repl` (`postprocess/repl.rs`). A principal effectively holds a replication right on a domain if it, or a group it transitively belongs to through `MemberOf`, has the `GetChanges` / `GetChangesAll` edge to the domain; the two rights may come through different groups. The edge starts where the pair first completes: at a principal holding both rights itself, or whose effective rights complete the pair while none of its direct parent groups' do. Members below reach it through `MemberOf`. This is BloodHound CE's `CalculateCrossProductNodeSets` rule, except that CE also gives an edge to a direct holder of GetChanges below a group completing the pair (path-equivalent here). A right held by Authenticated Users or Everyone (or a group containing them) counts for every principal, as in CE. `GenericAll` / `AllExtendedRights` on the domain are already traversable edges and are not counted. |
| `SyncLAPSPassword` | yes | Same pass and rule with `GetChanges` + `GetChangesInFilteredSet`, from each syncer to every computer of the domain with `haslaps` (CE). Deviation: principals whose effective rights also complete DCSync get no SyncLAPSPassword edges (DCSync already yields the domain; by default Administrators and the DC groups hold all three rights, so CE's rule would add one edge per LAPS computer per such group). LDIF and AD Explorer input decode the `GetChangesInFilteredSet` ACE (`89e95b76-…`) like SharpHound. |
| `AddMember` / `AddSelf` | yes | Taken from collector ACEs (WriteProperty on `member`, Self-Membership validated write, and manager-can-update-membership). Group-held rights are traversed through `MemberOf` at query time, not copied to each member: per-member edges would multiply edge counts and turn every remediation into N edges in choke-point analysis. |

## Entra ID roles

**Scoped role assignments.** Entra ID directory roles can be assigned
tenant-wide (`directoryScopeId` `/`), over an administrative unit, over one
application, or over one object. AzureHound rewrites every non-`/` scope to
`/<appId>` of the expanded `directoryScope`, so administrative-unit scopes (no
appId) look tenant-wide; it still writes the expanded `directoryScope` object
(`id`, `@odata.type`, `displayName`), which identifies them. BloodHound CE reads
only `directoryScopeId` and treats such assignments, and app-scoped ones other
than (Cloud) Application Administrator, as tenant-wide. CopperHound
(`azurehound.rs`, `role_scope`):

| Scope | Edges |
|---|---|
| tenant (`/`, empty `directoryScope`) | principal `AZHasRole` → tenant role node, unchanged: all tenant-wide rules (`AZGlobalAdmin`, `AZResetPassword`, `AZAddMembers`, …) and Tier Zero apply |
| application, (Cloud) Application Administrator | principal `AZAppAdmin` / `AZCloudAppAdmin` → AZApp (as CE) |
| application, other roles; single object (user, group, service principal, device) | principal `AZHasRole` → **scoped role node** `<roleDefinitionId>/<scopeId>@<tenant>`, named "<role> (scope: <name>)", with `AZScopedTo` → the scope object. The `azure` pass derives the tenant-wide rule restricted to that object: `AZResetPassword` if the role could reset that user, `AZAddMembers` for that group, `AZAddSecret` / `AZAddOwner` for that app or service principal, `AZExecuteCommand` for that Windows device |
| administrative unit | principal `AZHasRole` → scoped role node, `AZScopedTo` → an untyped node for the AU. AzureHound collects neither AU objects nor AU membership, so the scoped role grants no edges |
| unrecognised `directoryScope` type | like an AU: visible, no derived edges |

The scoped role node is not contained by the tenant, so tenant-wide rules never
see it; its id does not start with `<template>@`, so an AU-scoped Privileged
Authentication Administrator is not Tier Zero. Its properties (`scoped`,
`scopeId`, `scopeType`, `scopeName`, `roleDefinitionId`, `tenantId`) keep the
assignment queryable. For the password-reset rules, a user holding a role at
any scope counts as a role holder (Entra checks the target's roles regardless
of scope), so a Helpdesk Administrator cannot reset a user who is, say, an
AU-scoped Privileged Authentication Administrator. Eligible (PIM) assignments
at a non-tenant scope are still skipped (as CE).

**PIM approvers** (`AZRoleManagementPolicyAssignment`, CE
`ConvertAzureRoleManagementPolicyAssignment`). When a tenant-scope role's PIM
policy requires approval, each listed approver user or group gets
`AZRoleApprover` → the role; when no approver is listed, the Privileged Role
Administrator and Global Administrator roles do. `AZRoleApprover` is not
traversable in CopperHound (CE traverses it): an approver cannot approve its own
activation, so approval alone does not grant the role. The policy properties are
not copied to the role node.

## Hybrid

The `hybrid` pass (`postprocess/hybrid.rs`) runs only when both AD and
AzureHound data are loaded.

| Edge | Traversable | Source → target | Semantics |
|---|---|---|---|
| `SyncedToEntraUser` | yes | AD User → AZUser | Entra user with `onPremisesSyncEnabled`, matched by `onPremisesSecurityIdentifier` = AD SID, else by `onPremisesImmutableId` (base64 objectGUID, the default source anchor) = AD `objectguid`. Password hash sync / PTA: the on-prem password is the cloud password. |
| `SyncedToADUser` | yes | AZUser → AD User | Reverse direction (password writeback). |
| `SyncedToEntraGroup` | yes | AD Group → AZGroup | Same matching for groups. Members of the AD group are members of the cloud group, so AddMember on the AD group grants the cloud group's roles. |
| `SyncedToADGroup` | no | AZGroup → AD Group | Informational. Synced group membership is mastered on-premises. |
| `EntraConnectCredentials` | yes | Computer → MSOL_ user / Sync_ AZUser | The Entra Connect server stores both sync credentials. Local admin can decrypt them (e.g. AADInternals `Get-AADIntSyncCredentials`). |
| `SeamlessSSO` | yes | AZUREADSSOACC computer → AZUser | Every synced user whose on-prem SID is in the computer's domain. The account's Kerberos key lets you forge a service ticket for any of these users and exchange it at Entra ID for their sign-in. |
| `AZResetPassword` | yes | Directory Synchronization Accounts role → synced AZUser | The sync account can set the password hash of any synced user of its tenant. |

**Detection.**
- AD sync account: a User named `MSOL_*`, or whose description mentions (Azure) Active Directory Connect / Entra Connect. The server is taken from "running on computer X" in the description.
- Entra sync account: an AZUser holding the Directory Synchronization Accounts role, with UPN `Sync_<server>_<hex id>@…`, or with display name "On-Premises Directory Synchronization Service Account". The server is taken from the UPN.
- The server name is resolved against Computer short names. If several computers share the name, the one in the MSOL account's domain is preferred.

**Tier Zero.** After the passes, the pipeline tags these as Tier Zero on both
sides (`postprocess::tier0_nodes`, reported as `post.tier0_added`):
- MSOL_ and Sync_ accounts
- the Entra Connect server
- AZUREADSSOACC

The MSOL account's DCSync / ForceChangePassword power comes from its ACEs as
usual. Entra Tier Zero roles are Global Admin, Privileged Role Admin, Privileged
Authentication Admin, Partner Tier2 Support, Hybrid Identity Admin and Directory
Synchronization Accounts, plus the tenants. Holders of these roles, and service
principals with RoleManagement.ReadWrite.Directory /
AppRoleAssignment.ReadWrite.All, are not tagged Tier Zero themselves; they reach
it through `AZHasRole`, `AZGlobalAdmin`, `AZMGGrantRole` and `AZMGGrantAppRoles`
and show up as exposed principals.

**Unified Tier Zero** (`EdgeFilter::unified_tier0`, server setting
`analysis.unified_tier0`, default on). AD and Entra Tier Zero are one target
set, and exposure, choke points and paths cross the hybrid boundary. When off,
no edge between an AD object and an Azure object is followed, and AD principals
are measured against AD Tier Zero only, Entra principals against Entra Tier
Zero only.

|---|---|---|---|---|

| `AdminTo` | yes | The source principal is a member of the local Administrators group of the target computer (from local group collection). | Execute code remotely as SYSTEM (service creation, scheduled tasks, WMI) and harvest the credentials of logged-on users from LSASS and the local SAM / LSA secrets. | Remove the principal from the computer's local Administrators group (or the GPO / Restricted Groups setting that adds it); use Windows LAPS for local administrator passwords and tiered administration so that admins of one tier never administer another. |
| `HasSession` | yes | A session of the target user was observed on the source computer.
